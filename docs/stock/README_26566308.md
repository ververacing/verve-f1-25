dumped 2026-11-16. Read-only `db get` only. The game and launcher weren't running (checked before every batch, and

## 4. Season question: the rows are shared

**2025 and 2026 use the same driver rows.** There is one `entrants.drivers.driver` table (197 rows, the same count as on
25251167), and none of its labels is season-specific. The seasons are split on other tables:

- **Grids.** `entrant_list_15` = `f1_2025` (season_2025, 20 seats) and `entrant_list_34` = `f1_2026` (season_2026,
  22 seats incl. Cadillac). The f1_2026 seats point at entrants `f1_2026-<label>` (entrant_121..142), and those carry
  `driver <label>`. For example, `f1_2026-lando_norris` has `driver lando_norris`, the same row that the 2025 entrant
  `lando_norris` uses. Only `driver_customisation` differs (`2026-mclaren_lando_norris` vs `2025-mclaren_lando_norris`).
  In the full-dump test, max_verstappen and alex_albon each resolved to one row index on both lists (driver_10 and
  driver_59).
- **Game modes.** `game_setup_mode` f1 (F1 2025) uses entrant setup `f1`, and f1_26 (F1 2026) uses `f1_26`, whose only
  lists are f1_2026 and f1_2026_equal_performance.
- **Career data groups.** `career.career_setup.CareerSetupDataGroup` has two rows, `f1_career_2025` and
  `f1_career_2026`. They name drivers by row label (both spawn `lewis_hamilton`). The career entrant lists reference
  f1_2025 or f1_2026 plus that season's driver pool and reserves.
- **Per-season data on a shared row:**
  - `entrants.drivers.seasonal_infos` has 2 rows: `max_verstappen` (game_setup_modes f1, seasons 2023/2024/2025,
    car number 3) and `lando_norris` (f1_26, season_2026, uses #1).
  - The statistics datasets split `default` and `2026` (game_setup_modes f1_26, seasons season_2026) inside one
    holder per driver.
- **Seasons table.** `game_setup.seasons` lists season_2023 to season_2026.

So a `driver_characteristics` write lands in both seasons. A season-specific value can only go through the statistics
datasets, or by choosing which season's values to write, as `verve_build_design.md` §5 already assumes.

## Not done yet / didn't resolve

- The full dump (ratings at x=0 for both datasets, plus all 84 `ai_driver_config` keys, for all 24 grid drivers) was
  stopped at 9 of 25 rows to free the game. That partial output isn't committed. In it, all 84 keys were identical
  across the 9 rows (Verstappen, Hamilton, Norris, Sainz, Hadjar, Albon, Perez, Bottas, Lawson) and to 25251167.
- `f1_career_2025`, `f1_career_2026` and `f1_career_2026_driver_pool` have no entrant table of their own; the first
  two are reference-only lists.
- Why it's slow: every value is one `swofty.exe` process, about 1.4 s each (mostly startup and database load), and
  `db get` on a row doesn't list `ai_driver_config`. So the 84 keys take 84 separate calls per driver: about 100 calls
  and 2.5 min per driver, about an hour for 25 rows. Ways to batch it, best first:
  1. one `db get` that takes many paths, or a `--recursive` / JSON dump of a row including the hash-only keys (needs
     a launcher feature);
  2. read `ai_driver_config` once from `default_driver` and spot-check a few rows, since all 84 keys were identical
     across every dumped row on both builds;
  3. run several slices in parallel (3 to 4 processes worked fine here, read-only).
