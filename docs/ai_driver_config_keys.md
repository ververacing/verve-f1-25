# `ai_driver_config` key catalogue (per driver, 84 keys)

Generated by `tools/build_catalogue.py`; edit that file, not this one. Scope: every key lives on `entrants.drivers.driver_N` and is **identical on all 197 stock rows** (RE note, `re/db/subsystems/ai.md` inbox 2026-10-29). None of these keys is in the launcher's key catalogue (`row_keys.txt.gz`). That does not block a plain `set`: `dbx.rs::set_text` resolves the key by its FNV hash and keeps the stock type tag (`packages/core/src/activation/dbx.rs`). It does matter for `add-row` copies of a driver (Driver Manager, Classic Seasons), where the names must be declared in the op file's `fields` block; Classic Seasons ships the full list in `addons/classicseasons/classic-seasons-2024/db/season.json`.

**Important discrepancy to resolve:** the parser notes in `re/db/functions.tsv` say these sections come "from ai_vehicle_config", but the leaf names match the per-driver `ai_driver_config.*` keys exactly, and the 2026-10-29 inbox note says `ai_driver_config` is parsed per driver (`0x142463b40 -> 0x14065dc50 at 0x14246671e`, `default_driver` copy at `0x14249a4f0`). The per-car `ai_vehicle_config` has its own, differently named `blocking` (5 keys), `overtake` (4 keys) and `exit_fallibility` (4 keys) groups. Treat the function notes' attribution as loose wording until a trace confirms which struct each parser fills.

Rating: **A** consumer located and decoded, tune now. **B** direction hypothesised from the name, consumer not traced, vary in small steps and verify. **C** controller-level, geometric or rules; do not touch until traced.

Totals: A = 11, B = 32, C = 41.
